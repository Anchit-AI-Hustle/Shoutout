Mapping the 80

The uploaded playbook is titled 100 prompts and contains 80 — Parts I to VIII, numbered 1 to 80. Here is what each one is worth on this build.

The conflict that matters mostThe generic playbook enforces ownership with an application-level check — compare userId in a controller. That is not sufficient for SHOUTOUT. Competing managers share one database and you hold payout data. Isolation has to be enforced at the row level in Postgres, so that a route someone forgets to guard still returns nothing. The playbook never mentions row-level security once.
Other stack conflictsIt assumes Express and MongoDB (you are on Next.js App Router and Supabase Postgres), hand-rolled JWT in localStorage (Supabase Auth, phone-OTP first, tokens never in localStorage), Bull only (you need Inngest for month-long lifecycle workflows and BullMQ for the generation pipeline), Stripe (an Indian payment aggregator, because you cannot legally hold funds), and email-first messaging (WhatsApp is the rail here).

F

Foundation

W1–2

Nothing ships until org isolation is proven by a test that runs on every commit.

12 prompts

F1

Monorepo bootstrap

Initialize the SHOUTOUT monorepo at shoutout-platform.

Structure:
  apps/web      Next.js 15 App Router, TypeScript, Tailwind, shadcn/ui
  apps/admin    internal HITL queues
  apps/workers  Python FastAPI, Dockerised — audio, ML, transcode
  packages/intent      @shoutout/intent (semantic engine, ported)
  packages/studio-core generation pipeline (ported)
  packages/match       scoring engine, one engine for all Shout types
  packages/money       settlement abstraction, PA-agnostic
  packages/db          Supabase client, generated types, RLS tests
  packages/ui          design system
  workflows/           Inngest functions
  supabase/migrations/

Include: pnpm workspaces, turbo, shared tsconfig, ESLint + Prettier,
Husky pre-commit, .env.example per app, GET /api/health returning
DB and worker status.

Do NOT create a separate Express backend. Route handlers in apps/web
plus service functions in packages are the backend.

apps/web:

Write a Zod schema validating every variable at boot. The process must

Separate dev / staging / prod. Never commit real values.
F3

Supabase project and migration 001

Create the SHOUTOUT Supabase project and write migration 001.

Migration 001 must establish, before any domain table exists:
  - orgs table (the tenant boundary)
  - org_members table (user to org, with org-scoped role)
  - a current_org_id() helper reading from JWT claims
  - RLS enabled by default on every schema
  - a template RLS policy pair (select / write) other tables will follow

Every domain table added later carries org_id NOT NULL and references
orgs. There is no exception to this and no retrofitting later.

Give me this migration alone. I will run it and paste the output before
you write 002.
F4

RLS test harness — blocking gate

Build the row-level security test suite for SHOUTOUT.

Create two seeded orgs, A and B, each with a member. Then, for every
table in the schema, assert that a session authenticated as org A:
  - cannot SELECT any row belonging to org B
  - cannot INSERT a row with org_id = B
  - cannot UPDATE or DELETE any row of org B
  - cannot escalate by setting org_id in a payload

Make the suite enumerate tables from information_schema so a new table
with no policy FAILS the suite automatically rather than passing silently.

Wire it into CI as a blocking gate. A policy regression is not a P2 in
this product — competing managers share this database and it holds
payout data.
F5

Identity model

Write migration 002: the SHOUTOUT identity model.

  orgs        id, type (manager|agency|self), name, gst, pan,
              kyc_status, plan_tier
  artists     id, org_id, stage_name, genres[], home_city, verified,
              shoutout_id (public stable identifier)
  roster      org_id, artist_id, commission_pct, exclusive,
              start_date, end_date
  profiles    person-level: display name, phone, avatar, languages[]
  org_members user_id, org_id, role

Rules:
  - a self-managed artist is an org with a roster of one and commission 0
  - the upgrade path from one artist to five must require no migration
  - shoutout_id is the stable public identifier credits will point at

RLS policies for all five tables, following the 001 template.
F6

Auth — phone OTP primary

Implement authentication for SHOUTOUT on Supabase Auth.

  - phone OTP as the primary path (India is phone-first, and audition
    entry cannot ask 45,000 people to create a password)
  - Google OAuth secondary
  - PKCE with the code exchange in a server-side route handler, never
    on the client
  - org context resolved server-side from session, never from a
    client-supplied parameter
  - middleware routes by org role for UI only; authorisation is RLS

Also: an onboarding step that creates an org for a new user, so there
is never a user without a tenant.

Do not hand-roll JWT, bcrypt or refresh-token rotation.
F7

Design system package

Build packages/ui for SHOUTOUT.

Base on shadcn/ui with a deliberate design position — this is not a
default Tailwind theme. Tokens split by surface:
  - culture surfaces (Stage, Collab, Liner): warm, high-contrast
  - money surfaces (Settle, Advance): precise, quiet, numerate

Components: Button, Input, Select, Combobox, Card, Sheet, Dialog,
Table, DataList (mobile card fallback for dense tables), Toast,
StatusPill, MoneyValue (dual currency INR and USD at a single
configurable rate), EmptyState, Skeleton.

Mobile first. Minimum 44px tap targets. WCAG 2.2 AA. Dense tables must
degrade to stacked cards below 760px, not horizontal scroll.
F8

Workers service skeleton

Stand up apps/workers for SHOUTOUT.

Dockerised FastAPI with Alembic, following the Third Eye backend
pattern. Endpoints stubbed now, implemented in Phase Studio:
  POST /analyze    BPM, key, genre via Essentia or librosa
  POST /transcribe lyric transcription, multi-language incl. code-switch
  POST /embed      text embeddings for match
  POST /separate   stem separation

Include: health endpoint, structured logging, request signing between
web and workers, and a docker-compose for local development.

Stand this up now even though it is empty — Studio lands in week 7 and
the deployment path should already be proven.
F9

Inngest workflow layer

Wire Inngest into SHOUTOUT as the lifecycle engine.

This is the LifeCycle-OS trigger layer, productised. Set up the client,
the serve handler, and one worked example: a hold-expiry function using
step.sleepUntil that fires at the release deadline and transitions the
hold to released.

Why Inngest and not cron: these workflows are long-lived, stateful and
human-in-the-loop, spanning months. Hold expiry, payout SLA escalation,
the T+11-month re-book, rejection-to-onboarding. Durable execution with
replay is the correct primitive.

Note: the Studio generation pipeline uses a separate BullMQ queue.
Two queues, different jobs. Do not merge them.
F10

WhatsApp template pipeline

Set up WhatsApp Business Cloud API for SHOUTOUT via a BSP.

Submit these templates for approval TODAY — approval takes 2 to 3 weeks
and blocks week 5:
  shout_answered, shout_slot_filled
  hold_expiring_48h, hold_challenged
  quote_sent, contract_ready, contract_signed
  advance_received, rider_confirm_t7, rider_confirm_t2
  payout_sent, payout_delayed
  audition_received, audition_result
  split_sheet_ready

Build: a send abstraction with template name and typed variables,
delivery-status webhook capture, a per-template delivery rate metric,
and an alert below 97%.

Email is the secondary rail. Build it after.
F11

Observability and audit

Add observability to SHOUTOUT.

Application: Sentry, structured logs, PostHog for product events.

Separately — and this matters more — an immutable audit log for
contracts, holds, settlements and splits. Append-only. Never updated.
Every state change writes actor, timestamp, before state, after state.
Disputes in this industry are routine; the log is the referee.

Alerts on: hold-expiry job failure, settlement reconciliation mismatch,
payout failure, WhatsApp template delivery below 97%, and any RLS
policy error in production.
F12

CI/CD with blocking gates

Set up CI/CD for SHOUTOUT on GitHub Actions.

Pipeline: lint, typecheck, unit tests, RLS suite, build, deploy.

Blocking gates — deployment fails if any of these fail:
  - the RLS cross-tenant suite
  - the settlement reconciliation test (splits must sum to zero)
  - the hold state machine test (no double-confirm on one date)

Supabase branching for database preview environments. Vercel preview
deploys per PR. Migrations run before code deploys, never after.
S

The Shout object

W3–5

The highest-leverage build in the company. Every other module is a specialisation of this.

8 prompts

S1

The polymorphic Shout schema

Write the SHOUTOUT Shout schema — the core of the entire product.

A Shout is a call that someone answers. One object serves five types:
Collab, Gig, Open (audition), Brand, Sync.

  shouts       id, org_id, type, title, body, status, visibility
               (open|invite|roster|verified), deadline, city,
               intent jsonb (a GENERATION_INTENT object), created_by
  shout_slots  id, shout_id, role, attributes jsonb, comp_model
               (fee|points|hybrid|credit), fee_amount, points_pct,
               deadline, status, filled_by
  answers      id, slot_id, responder_org_id, responder_artist_id,
               pitch, media_url, status, created_at

Requirements:
  - slots fill INDEPENDENTLY. A Shout can be half-closed.
  - one Shout can carry a songwriter slot and a vocalist slot on
    entirely different terms
  - comp_model 'credit' must be explicitly labelled and never default
  - RLS: visibility governs read; only the owning org can write

Do not model this as five separate tables. Resist that.
S2

Shout lifecycle state machine

Implement the Shout and slot state machine for SHOUTOUT.

Shout:  draft -> open -> partially_filled -> filled -> closed
        exits: cancelled, expired
Slot:   open -> answered -> shortlisted -> accepted -> contracted
        -> delivered -> settled
        exits: withdrawn, declined, expired

Enforce transitions in the database with a trigger, not in application
code. An invalid transition must be rejected by Postgres.

Every transition emits an Inngest event carrying the actor and both
states. Those events drive notifications and the audit log.
S3

The match engine

Build packages/match for SHOUTOUT — one engine, all Shout types.

  score = role_match
        x attribute_fit
        x availability
        x price_band_fit
        x reliability
        x responsiveness

attribute_fit is the differentiator. Match a slot's requirements against
a responder's declared attributes: vocal range against the song key,
language against lyric language, timbre tags against mood, BPM comfort,
turnaround against deadline.

Semantic layer: embeddings over the GENERATION_INTENT object in pgvector,
so 'nocturnal, restrained, late-night' matches a vocalist tagged
'smoky, low-register, R&B' without either party using the same words.
Hybrid with Postgres full-text. Do not add a search cluster.

Return ranked results with a score_components breakdown — the breakdown
is shown in the UI, because an unexplained ranking is not trusted.

Availability must be checked live against the holds ledger. Never
surface someone already held on that date.
S4

Intent capture — port @shoutout/intent

Port the MusicGenAI semantic engine into packages/intent.

Source: the 19-field form to deterministic GENERATION_INTENT JSON
converter, plus the AI-suggest system that ENHANCES existing user input
rather than replacing it (field-specific prompts, lower temperature for
enhancement, higher for generation from scratch).

Target: a versioned internal package with a Zod schema for
GENERATION_INTENT and parity tests against the original.

This object has four consumers — Studio generation, Collab matching,
sync catalog tagging, gig genre matching. Design the package for four
callers, not one.

Write the parity test suite first. Archive the MusicGenAI repo only
after it passes.
S5

Shout composer

Build the Shout composer UI for SHOUTOUT.

One composer, type-aware. Steps:
  1. what kind of Shout
  2. describe it — free text, with AI-suggest from @shoutout/intent
     enhancing what the user wrote
  3. add slots — role, attributes, terms, deadline, per slot
  4. attach a reference (upload, or generate in Studio)
  5. visibility and publish

Mobile first, resumable as a draft, under 90 seconds for the common
case (one slot, open visibility).

Copy rule: the verb is 'put out a shout'. Never 'create a listing',
never 'post a request'.
S6

Answer flow

Build the answer flow for SHOUTOUT.

A responder sees a Shout, picks a slot, and answers with a pitch plus
optional media — for a Collab slot, a 30-second demo recorded against
the actual attached beat.

  - answer limits per responder per day, to prevent spam
  - the poster gets a ranked answer list with score breakdown
  - shortlist, decline with a reason, or accept
  - accepting a slot opens a Room (Collab) or a hold (Gig)

Notify on every state change via WhatsApp template.
S7

Discovery feed

Build the SHOUTOUT discovery feed.

Two directions:
  - 'Shouts you could answer' — ranked by fit against declared roles
  - 'People who could answer yours'

Filters: role, genre, language, city, remote vs in-person, paid vs
points, deadline. Infinite scroll. URL-persisted filters.

Habit mechanic: a daily digest of three high-fit Shouts, delivered by
WhatsApp. This is the retention loop — collaboration is the only module
with a genuine daily reason to open the app.
S8

Reliability score

Implement the SHOUTOUT reliability score.

Per ROLE, not per person — a great producer can be an unreliable mix
engineer.

Inputs: on-time delivery rate, revision adherence, split disputes
raised against them, response latency, completion rate on accepted slots.

Design rules:
  - decays with inactivity so dormant accounts do not hold rank
  - new users get a provisional band, never a zero. A cold-start
    penalty kills supply.
  - visible to both sides, with the inputs shown

Feeds directly into match scoring.
C

Collab network

W5–8

No cold start, daily habit, and it populates the credits registry for free.

8 prompts

C1

Role taxonomy and profiles

Build role-based profiles for SHOUTOUT.

Role families and their match attributes:
  Voice        vocalist, topliner, rapper, backing, harmony, VO
               -> range, timbre tags, languages, accent, key comfort
  Writing      songwriter, lyricist, hook writer, composer, arranger
               -> languages, themes, co-write vs work-for-hire
  Production   beat producer, instrumental, sound design, programmer
               -> genres, BPM range, typical keys, DAW, turnaround
  Engineering  mix, mastering, vocal edit, tuning
               -> genre specialism, stem capacity, revision policy
  Players      guitar, bass, drums, keys, tabla, sitar, flute,
               strings, brass, percussion
               -> instrument, style, reading vs by-ear, remote vs live
  Stage        DJ, live band, hype, MD, backline tech, FOH
  Visual       video director, DOP, editor, VFX, cover art, stylist
  Business     manager, agent, publicist, scout, studio owner

Many-to-many: one person, several roles. Matching happens per role,
never per person. Each role carries proof of work — audio or video
samples, and credits.
C2

Collab Rooms

Build Collab Rooms for SHOUTOUT.

Opens automatically when a slot is accepted. Contains:
  - versioned stem uploads, immutable, full history
  - reference tracks
  - threaded chat with presence via Supabase Realtime
  - the split sheet
  - deadline countdown
  - escrow state
  - revision counter against the agreed policy

Version discipline: every upload is versioned and immutable. Disputes
are resolved from version history, which makes the Room the evidence log.

Mobile first — people record vocals on a phone.
C3

Split sheet — gates file transfer

Implement split sheets for SHOUTOUT. This is the most important rule
in the module.

NO full-quality stems are released until every slot's split is agreed
and signed. Watermarked previews only before that point. There is no
path around this and no override.

Capture:
  - writer share and master share, declared SEPARATELY
  - work-for-hire vs co-write per contributor
  - publisher or PRO affiliation if known
  - territory and term if non-standard

On signature: write directly into SHOUTOUT Credits. This is how the
registry populates without anyone doing data entry — the single
highest-leverage automation in the company.

The industry's oldest problem is undocumented splits discovered years
later when money finally arrives. Make the split a precondition of the
file transfer, not an afterthought.
C4

Watermarked stem exchange

Build watermarked media exchange for SHOUTOUT.

  - audible watermark on preview streams, no download
  - full files unlock on split signature and, for paid slots, on
    escrow funding
  - applies to beats going OUT and vocal takes coming BACK —
    protection runs both directions
  - signed, expiring URLs; never a public bucket path
  - watermarking runs in apps/workers, not in the request path
C5

Escrowed delivery

Implement escrowed delivery for Collab slots in SHOUTOUT.

Runs on the same Settle rail as gigs — do not build a second payment path.

  - fee slots fund on signature
  - release on delivery acceptance, or auto-release after a review
    window
  - milestones for larger jobs: demo, full take, revisions
  - revision policy declared on the slot BEFORE anyone applies;
    exceeding it triggers a priced change request, not an argument
  - dispute freezes escrow and preserves version history as evidence
C6

Demo-to-Shout

Build demo-to-Shout for SHOUTOUT.

Upload a hum, a phone voice note, or a rough loop. Then:
  1. apps/workers extracts BPM, key and mood
  2. @shoutout/intent drafts a GENERATION_INTENT
  3. the composer opens pre-filled
  4. the user confirms and posts

This is the lowest-friction entry path in the product, and it converts
the least articulate users — often the most talented ones — into posters.

Target: voice note to published Shout in under 60 seconds.
C7

Trust and safety

Implement trust and safety for the SHOUTOUT Collab network.

  - verified identity (phone plus PAN or equivalent) required before
    any PAID Shout; free collabs stay lighter-weight
  - work-for-hire vs co-write declared up front on every slot —
    ambiguity here is where relationships die
  - dispute path that freezes escrow and surfaces version history
  - report and block, per person and per org
  - rate limits on Shout posting and answering
  - detection for: duplicate profiles, collusive reviews between two
    orgs, escrow abuse patterns, and stem leakage
C8

Collab-to-release handoff

Build the collab-to-release handoff for SHOUTOUT.

On Room close:
  - credits registered against every contributor's shoutout_id
  - a work record created
  - optional push into the sync catalog with splits pre-registered
  - a release campaign scaffolded in Growth OS, with every
